# How PipeWire applications connect and what the RTC can simplify

**Recommendation.** Give an instrument's loaded controller graphs a lifetime independent of the operator's RTC session. Let one MediaSession subscribe to the private core, match the declared roles as their endpoints appear, create the required Links and admit the held graph. A routine MediaSession update could then reconnect to controllers already loaded with the right calibration. A controller update or a cold instrument start would still load the affected graphs. This is a proposed service-lifetime change to the RTC at `5bc01d2`. The timings below describe the existing implementation.

## How applications use PipeWire

| Application | What the upstream implementation actually does | Lesson for the RTC |
| --- | --- | --- |
| **pw-record / pw-play** | The two modes of `pw-cat` connect to the core, publish a stream and its acceptable formats, then enter the main loop. They handle stream-state, format and buffer callbacks. By default the stream requests autoconnection. A caller can specify a target. On a WirePlumber desktop its policy chooses and links a compatible endpoint and can reroute on loss. [Client source](https://github.com/PipeWire/pipewire/blob/1.6.8/src/tools/pw-cat.c#L2612-L2645) · [Target selection](https://github.com/PipeWire/pipewire/blob/1.6.8/src/tools/pw-cat.c#L2289-L2303) · [WirePlumber linking policy](https://pipewire.pages.freedesktop.org/wireplumber/policies/linking.html) | Useful model for a detector publishing its output. An RTC must select the declared detector and handle its loss explicitly. |
| **qpwgraph** | This patchbay opens a core connection and listens to the registry. To connect two ports it passes the current node and port IDs to the native Link factory. Its manual patch cords use `object.linger=true` so they can survive the tool disconnecting. [Registry](https://github.com/rncbc/qpwgraph/blob/60aba1ea8bc95cc67ff52db593131936da746e6a/src/qpwgraph_pipewire.cpp#L736-L762) · [Link creation](https://github.com/rncbc/qpwgraph/blob/60aba1ea8bc95cc67ff52db593131936da746e6a/src/qpwgraph_pipewire.cpp#L875-L908) | Use the registry model and explicit linking. Keep RTC-owned Links non-lingering so loss of the session drops its routes. |
| **EasyEffects** | Its manager watches nodes, ports and Links. Each processing plugin publishes a filter and ports. It waits for the filter's ID and the expected port count, including 1 ms polling. The output pipeline connects filters from downstream to upstream and retains the resulting proxies. [Manager](https://github.com/wwmm/easyeffects/blob/18bb4cd33d3c10053fd59523001fe0c92e1354ed/src/pw_manager.cpp#L417-L440) · [Filter startup](https://github.com/wwmm/easyeffects/blob/18bb4cd33d3c10053fd59523001fe0c92e1354ed/src/plugin_base.cpp#L483-L532) · [Pipeline wiring](https://github.com/wwmm/easyeffects/blob/18bb4cd33d3c10053fd59523001fe0c92e1354ed/src/stream_output_effects.cpp#L318-L349) | A multi-stage native application also needs discovery, ordering and evidence that ports exist. Its filters can share a manager and process. A separate launch and identity handshake per scientific algorithm is an application design choice. |
| **Ardour using JACK on PipeWire** | Ardour opens its JACK client if needed, reads the actual sample rate and buffer size, re-establishes ports, installs callbacks, activates the engine and reconnects routes. With PipeWire's JACK library these calls reach PipeWire. Ardour's engine activation precedes route restoration in this backend. [Ardour startup](https://github.com/Ardour/ardour/blob/e5e3257bdbae91e6c81e4d264ba46ade58693e23/libs/backends/jack/jack_audiobackend.cc#L483-L530) · [PipeWire JACK compatibility](https://docs.pipewire.org/page_man_pw-jack_1.html) | Separate engine lifetime, routing and permission to process. Our public Ready still requires all mandatory routes and held controllers. Closing an AO loop is a later operator action. |

Two upstream mechanisms matter for the design. In PipeWire 1.6.8, `pw-link` can submit multiple Link creation requests and receive each result through listeners. It tracks all requested Links until each has reached a definitive state. Its one-shot command records the first such result. The RTC also needs ongoing loss handling. A matching `pw_core_sync` reply orders earlier operations on that connection. Negotiated Link state, controller Hold and valid science data each require their own observations. [Link submission](https://github.com/PipeWire/pipewire/blob/1.6.8/src/tools/pw-link.c#L495-L599) · [Link completion](https://github.com/PipeWire/pipewire/blob/1.6.8/src/tools/pw-link.c#L130-L148) · [Core synchronization](https://docs.pipewire.org/group__pw__core.html)

PipeWire's filter-chain module also demonstrates a useful ownership boundary. A processing host keeps its internal DSP graph private and exposes input and output streams to other clients. FGN and Julia FilterGraphs already play this role for the RTC. Expose an additional node or process when independent placement, ownership, fault isolation or an external instrument contract justifies it. [Upstream filter-chain design](https://docs.pipewire.org/page_module_filter_chain.html) · [RTC ownership](../../architecture.md#accepted-workstation-integration-boundary)

## What is making our startup expensive

The instrument starts two graph processes even on a CAL2 session-only restart. The preparation process renders invocation-specific units and configuration, retains their live identities and only then starts MediaSession. MediaSession already has a registry listener, an event queue and a state machine. It drives owner discovery, owner connections, graph discovery, Link creation, Hold, native Status and publication through successive effects. The two graph-owner connections already run concurrently. Declared endpoints are resolved up front, but Link creation waits for each Link to finish negotiating before submitting the next in downstream-first order. [Unit preparation](../../../src/deployment/session_launch.jl) · [Startup effects](../../../src/media_session/effects.jl) · [Link creation](../../../src/media_session/objects.jl) · [Installed admission](../../../src/media_session/admission.jl)

In the 13.66 s CAL2 diagnostic, the RTC spent 3.13 s connecting to the starting graph owners, using 0.42 CPU seconds over that interval. It spent 6.52 s compiling Julia code after package initialization across the entire activation. Actual final core synchronization took 2.3 ms. Five offline precompilations subsequently reduced untraced Ready time to 12.11–12.30 s. These measurements distinguish controller startup, application code and a native round trip. The upstream source review supplies no cross-application startup benchmark. [Measurement boundaries and results](../../validation/session-owned-admission-20261123/startup-profile.md)

## Proposed changes in priority order

**PW-01 — Keep prepared graph owners across session-only restarts.** Make this an explicit supported deployment mode for compatible owners. Install stable owner units, graph files and a manifest of required roles, edges and placement. Start the source, graph owners and MediaSession independently once their actual prerequisites are available. Bind each role to its live process and native endpoint at activation. A changed graph, calibration, ABI or placement invalidates reuse for that owner. Keep the full cold-start and full shutdown paths. Existing sealed launchers retain their pinned behavior. The current contract rebuilds RTC-owned processes on explicit restart, so persistent ownership requires an explicit lifecycle decision. The HEART source that takes a live owner PID still has that dependency. **Highest expected impact on RTC-only restarts.** It removes entire process starts and graph loads from that operation. The end-to-end saving is unmeasured. [Existing startup contract](../../SYSTEMD_SESSION_STARTUP.md) · [Current ownership](../../architecture.md)

A reusable controller must return to Hold with correction open on loss of its controlling invocation, including abnormal exit. The retiring session loses its command authority. Drop its Links, pending operations, priming evidence and permission to apply corrections. A replacement session acquires a new identity and checks calibration, execution mode, generations, placement and held state before reusing the graph. Define the allowed held output in the instrument contract. Independent cameras and simulators can keep publishing throughout.

**PW-02 — Let registry and Link events drive each admission dependency.** Retain the existing MediaSession owner, HSM and bounded event queue. Resolve installed role names against the current unit invocation/process and the live PipeWire node, owning client, port direction and object serial. Retain that binding for the activation and invalidate it on removal, replacement, core loss, unsupported format or queue overflow. As the required owners and ports become available, issue independent requests in bounded groups. Within each permitted downstream-first group, create the Links and wait for the whole group's exact endpoints, directions, formats and negotiated states. Keep per-Link listeners, finite deadlines and cleanup of partially created groups. This removes the one-at-a-time wait for independent edges. For scale, the entire find/connect/hold interval in the profiled CAL2 build took 1.04 s. [Current capture and Link checks](../../../src/media_session/objects.jl) · [Current lifecycle](../../../src/media_session/machine.jl)

**PW-03 — Move static deployment work to installation; keep one live admission decision.** Resolve graph topology and validate configuration and artifact compatibility at install/update time. Use systemd's live unit identity and the registry to fill the few runtime-dependent fields. Read actual scheduling and CPU placement on activation. Keep changes of invocation or required objects observable through the final admission boundary. Preserve the fresh request and reply through the public native Status endpoint, the fault check, discovery publication and `sd_notify`. The published endpoint must still work for a client. A local state variable or an ordered core round trip alone cannot establish that. This is RTC application policy. A site WirePlumber policy can coexist, and generic transport primitives may belong in PipeWireAO. Installing a second coordinator in the core would give two components responsibility for one graph. [Deployment verification](../../../src/deployment/session_cli.jl) · [MediaSession authority](../../architecture.md)

**If the whole instrument must start from zero.** Persistent controllers accelerate a service replacement. A power-on start still pays for each runtime, graph and calibration. Start compatible owners in parallel with MediaSession once the core accepts clients. Where branches can share a process, compare one prepared graph host exposing the required external ports against one process per branch. Preserve independent thread placement and keep separate any owners that need fault isolation. For an instrument with equivalent native FGN operators, that host is also a candidate for a cold-start comparison. Neither approach requires an RTC policy module inside the PipeWire daemon. A cold-start target needs to include controller and calibration loading on both sides of any comparison with HEART.

**Operator sequence.** Ready means that all mandatory Links and held controllers have been verified. Start admits live input with every integrator open. GPI2 requires a usable pyramid measurement, Classic requires valid calibrated slopes, CAL2 SCC requires a usable chopped pair, and SPIDERS requires the measurements declared by its selected camera mode. Only an explicit operator Close after that controller is primed allows correction. A controller may retain its loaded code and calibration across restart while discarding all previous permission to correct. [Instrument-specific priming criteria](../../validation/open-loop-startup-20261123/README.md#instrument-startup-settings)

**First implementation test.** On private CAL2, keep both graph processes and the publishing simulator alive, stop only MediaSession, then start a fresh session against the same process identities. Compare that operation with a fresh start of all RTC-owned processes using the same installed images and source. Verify fresh Links, native Ready, both integrators Open, first usable live measurements and the signed first correction only after explicit closure. Kill the controlling session while running, replace an owner under the same name, and change calibration separately. Each case must withdraw the old authority and require fresh admission. Check ordinary Stop, full Quit and partial Link creation failure. Run the same lifecycle checks for GPI2, Classic and SPIDERS before declaring this the shared default. This review proposes a design and acceptance test; only the existing implementation has measured startup times.
